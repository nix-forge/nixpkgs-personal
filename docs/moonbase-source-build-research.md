# Can Moonbase be built from source?

Reviewed: 2026-09-24. Scope: the pinned Jellyfin Moonbase 2.2.0.0 package and its bundled Moonfin Web 2.5.1 client. The decision is whether the release ZIP can be replaced by an offline Nix source build without dropping the web client or misrepresenting the result.

## Answer

**Yes. The complete source build passed its package install check using two independently pinned builds.** The [Moonbase 2.2.0 tag](https://github.com/Moonfin-Client/Plugin/tree/2331a3a1d2721d3f348ab3e76dfa2db079f6917d) contains the .NET 8 Jellyfin server plugin. Its release ZIP also contains a Flutter web client from the separate [Moonfin-Core 2.5.1 tag](https://github.com/Moonfin-Client/Moonfin-Core/tree/f18c45b1fbf9b63871b4f93237179f9706154763). The Moonbase [release manifest](https://github.com/Moonfin-Client/Plugin/blob/2331a3a1d2721d3f348ab3e76dfa2db079f6917d/Jellyfin/manifest.json) names that web-client version. Rebuilding only the .NET assembly would remove most of the current package's payload.

The [package expression](../pkgs/by-name/je/jellyfin-plugin-moonbase/package.nix) builds the server and web client from the pinned source revisions. It verifies the release version and Jellyfin target ABI, preserves the web files and `assets/NOTICES`, and disables in-app updates. Its mixed provenance covers locally compiled code alongside retained NuGet assemblies, fonts, and WebAssembly runtimes. License metadata includes the plugin's GPL-3.0, the web client's GPL-2.0-or-later, and the identified bundled font and archive-runtime licenses.

Nixpkgs provides [`buildDotnetModule`](https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/dotnet.section.md) for the server and [a Flutter web target in `buildFlutterApplication`](https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/dart.section.md#flutter-applications). The Nixpkgs manual advises pinning a specific Flutter version. This repository's locked [Nixpkgs revision](https://github.com/NixOS/nixpkgs/tree/44a91898084f46797b5fac650c7e8c9ac38c43d4) contains a [Flutter 3.44.4 definition](https://github.com/NixOS/nixpkgs/blob/44a91898084f46797b5fac650c7e8c9ac38c43d4/pkgs/development/compilers/flutter/versions/3_44/data.json), while the upstream 2.5.1 web workflow used 3.44.1. The source build and install check passed with 3.44.4. Compiler parity would require a separately pinned 3.44.1 toolchain.

## Validation and limits

Inspection used the two exact upstream tags and the pinned release ZIP on Linux. The tag revisions came from `git ls-remote`; the archive inventory came from Python's `zipfile`. The .NET server and Flutter web derivations built from pinned source with offline dependency graphs. The 170 web file paths exactly match the release ZIP's frontend file paths; the release adds only two server assemblies and `meta.json`. Its three theme files also match byte for byte. No Jellyfin runtime test or bit-for-bit comparison of generated JavaScript and WebAssembly has run. The release ZIP includes a timestamped `meta.json`, so a byte-for-byte ZIP match is neither expected nor needed; functional file coverage and ABI compatibility matter.

The release notes associate Moonbase 2.2.0 with Moonfin Web 2.5.1, but the ZIP has no `build-manifest.json` recording its exact frontend commit. The `2.5.1` tag is the most defensible source pin, yet equivalence of its generated web assets to the release payload remains unverified. The package has pinned NuGet and Dart dependency graphs.

## Implication for this repository

The implemented two-stage composition compiles `Moonfin.Server.dll` from the plugin tag using `buildDotnetModule` and retains the pinned SharpCompress NuGet assembly; it builds the Flutter web files from the Moonfin-Core tag with a versioned Flutter builder, pinned `pubspec.lock` data, and hashes for the media-kit Git source; then assembles the release directory layout and derives `meta.json` from the source manifest with `autoUpdate = false`. The install check asserts the pinned Jellyfin ABI. A failed Flutter build cannot silently substitute an empty or upstream-hosted web directory.

The combined package built on x86-64 Linux. Its install check covered the web entrypoint, WebAssembly asset, theme, notices, DLLs, version, ABI, and disabled updates. The source-built web client had the release frontend file inventory. The upstream verifier and a live Jellyfin plugin load have not run; those remain useful checks when updating. The package preserves both source licenses and marks locally compiled code as `fromSource` and retained prebuilt assets as `binaryBytecode`. The plugin and web update pins remain separate so later releases can be reviewed together.
